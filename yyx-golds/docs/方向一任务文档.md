### 6.4 粒度决策：**流派分析绝不去重**（重要，写错整个方向就废）

实测：32,833 行里有 3,166 个 `track_id` 重复（共 7,643 行）。若按曲目去重：

| 指标 | 主表 32,833 | 去重后 28,356 |
|---|---|---|
| pop | 5,507 | 5,132 |
| rap | 5,746 | 5,401 |
| rock | 4,951 | 4,305 |
| latin | 5,155 | 4,137 |
| r&b | 5,431 | 4,504 |
| edm | 6,043 | 4,877 |
| 热度均值 | **42.48** | 39.33 |

原因：**1,687 个重复 track_id 同时出现在不同流派的歌单里，3,166 个重复 id 全部跨子流派**。一首歌本来就可以既是 pop 又是 edm —— 去重等于随机丢掉它一半的流派归属，edm/latin/rock 的供给量会被系统性压低（去重后 edm 从第 1 掉到第 2）。

**因此：本方向（方向一）全部 6 张图基于主表 32,833 行（歌单-曲目粒度），不做任何去重。**
同一 track 的 `track_popularity` 在重复行中完全相同（实测 0 条不一致），所以热度类指标不受影响，受影响的只有供给计数。

> 与"歌手/专辑方向"的区别：那边去重后是 28,356 行；本方向**不要**复用那个数字，任何地方写 28,356 都是错的。

`medianPopularity` 可选。要它就得再查一次（MySQL 没有 `PERCENTILE_CONT`）：

```sql
WITH ordered AS (
  SELECT playlist_genre, track_popularity,
         ROW_NUMBER() OVER (PARTITION BY playlist_genre ORDER BY track_popularity) rn,
         COUNT(*)     OVER (PARTITION BY playlist_genre) c
  FROM spotify_songs
)
SELECT playlist_genre AS genre, ROUND(AVG(track_popularity),0) AS median_pop
FROM ordered
WHERE rn IN (FLOOR((c+1)/2), CEIL((c+1)/2))
GROUP BY playlist_genre;
```

  track_popularity  TINYINT UNSIGNED NOT NULL COMMENT '0-100',
  popularity_bin    VARCHAR(8)     NOT NULL COMMENT '5 档',
  release_year      SMALLINT       NOT NULL COMMENT '1957-2020',
  release_month     TINYINT        NULL     COMMENT '仅年份精度为 NULL（1855 行）',
  date_precision    VARCHAR(8)     NOT NULL COMMENT 'day/month/year',

  KEY idx_genre      (playlist_genre),
  KEY idx_genre_sub  (playlist_genre, playlist_subgenre),

  KEY idx_genre_year (playlist_genre, release_year),
  KEY idx_popularity (track_popularity),
  KEY idx_pop_bin    (popularity_bin),
  KEY idx_track      (track_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin
  COMMENT='方向一：歌单-曲目粒度明细，未去重';

**导入脚本要点**（`data\02_import_to_mysql.py`，已跑通，32,833 行约 3 秒）：

## 13. 风险与降级（全部为本机实测踩到的真实坑）

### R1 · `mvn` 命令不存在
- **信号**：`'mvn' 不是内部或外部命令`
- **原因**：本机没有独立安装 Maven，只有 IDEA 内置的
- **降级**：全路径调用
  ```bat
  "D:\idea\IntelliJ IDEA 2025.3.2\plugins\maven\lib\maven3\bin\mvn.cmd" -s "D:\maven\settings.xml" -Dfile.encoding=UTF-8 spring-boot:run
  ```
  或把该 `bin` 目录临时加进 `PATH`。

### R2 · 离线构建失败（`-o` 一定失败）
- **信号**：`Cannot access mirror ... in offline mode and the artifact org.codehaus.plexus:plexus-compiler-javac:jar:2.8.4 has not been downloaded`
- **原因**：本地仓库 `D:\maven\repository` 只有 26 个 groupId，`maven-compiler-plugin` 的传递依赖缺失
- **降级**：**不要加 `-o`**，必须联网首次构建（阿里云镜像实测可用，`BUILD SUCCESS` 约 41s）。若确实断网，只能先在能上网的机器上 `mvn dependency:go-offline` 后把整个 `repository` 拷过来。

### R3 · 用 `spring-boot-starter-parent` 报找不到父 POM
- **信号**：`Non-resolvable parent POM ... spring-boot-starter-parent:2.7.6`
- **原因**：本地仓库没有 parent，只有 `spring-boot-dependencies` BOM
- **降级**：**照 `D:\Spring\SpringBoot\pom.xml` 的写法**——`<dependencyManagement>` 里 import `spring-boot-dependencies:2.7.6`，并在 `<build><plugins>` 里**显式钉版本**：`spring-boot-maven-plugin 2.7.6`、`maven-compiler-plugin 3.8.1`、`maven-jar-plugin 3.4.1`、`maven-surefire-plugin 3.2.5`。不钉版本，Maven 3.9.11 会去拿默认新版插件，联网慢、离线必挂。

### R4 · 中文/编码乱码
- **信号**：控制台中文变问号；页面接口返回中文乱码
- **原因**：本机 `mvn -v` 显示 `platform encoding: GBK`
- **降级**：pom 里 `<project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>`；启动加 `-Dfile.encoding=UTF-8`；JDBC URL 带 `useUnicode=true&characterEncoding=utf8`；`application.yml` 里 `server.servlet.encoding.force=true`。

### R5 · 建库继承了 `utf8mb3_general_ci`
- **信号**：`SHOW CREATE TABLE spotify_songs` 显示 `utf8mb3` / `utf8mb3_general_ci`
- **原因**：MySQL 服务端默认就是 `utf8mb3 / utf8mb3_general_ci`（实测），`utf8mb3` 存不了 4 字节字符，`general_ci` 大小写不敏感（`EDM` 与 `edm` 会被视为同值）
- **影响范围**：本数据集流派名全小写、无 4 字节字符，**不会立刻报错**，但一旦以后加中文流派注释或做 join 就会炸；且违反"库表统一 utf8mb4_bin"的口径约定
- **降级**：
  ```sql
  ALTER DATABASE spotify_genre CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;
  ALTER TABLE spotify_songs CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;
  ```

### R6 · `LOAD DATA` 用不了
- **信号**：`ERROR 3948 (42000): Loading local data is disabled` 或 `secure_file_priv` 相关报错
- **原因**：实测 `local_infile=0`、`secure_file_priv=NULL`
- **降级**：**不要改 my.ini**。用 `pip install pymysql` + Python `executemany` 导入，32,833 行约 5–10 秒。

### R7 · `key` 是保留字
- **信号**：`ERROR 1064 ... near 'key, loudness'`
- **降级**：SQL 里写 `` `key` ``；MyBatis 注解里同样要反引号。

### R8 · 导入时 `instrumentalness` 全变 0
- **信号**：导入后 `SELECT AVG(instrumentalness)` 返回 0.00
- **原因**：CSV 里 7,059 行是 `2.33e-05` 这类科学计数法，列若建成 `DECIMAL(10,4)` 会被截成 0
- **降级**：列类型用 `DOUBLE`，导入用 `float()`，不要用 `round()`。

### R9 · 趋势图最后一年断崖
- **信号**：2019 → 2020 突然从 9,081 掉到 785
- **原因**：抓取时点截断，2020 只有 785 行（2.39%）
- **降级**：`WHERE release_year BETWEEN 1990 AND 2019`，副标题注明"2020 年数据不完整，已截断"。

### R10 · 趋势图左侧被毛刺压扁
- **信号**：1990 年前的长尾把主图压成一条线
- **原因**：<1990 合计仅 2,447 行，平均 74 行/年
- **降级**：x 轴从 1990 起；若老师要求全量，改成 y 轴 `log` 或加"仅看 1990 年后"开关。

### R11 · 误按"歌手方向"去重导致数字全错
- **信号**：`edm` 变成 4,877、`latin` 变成 4,137，热度均值变 39.33
- **原因**：1,687 个重复 `track_id` 跨流派，去重会丢流派归属
- **降级**：本方向**一律用主表 32,833 行**，任何数字与 6.6 表不符就先查是不是加了 `DISTINCT track_id`。

### R12 · 端口被占
- **信号**：`Web server failed to start. Port 8088 was already in use`
- **降级**：8088 与 8080 当前都空闲；若被占，`server.port=8090` 并同步改前端 `API_BASE`。

### R13 · 装完包却 `ModuleNotFoundError`（本机最坑的一条）
- **信号**：`pip install pymysql` 显示成功，`python 02_import_to_mysql.py` 仍报 `No module named 'pymysql'`
- **原因**：本机 `pip` 指向 `...\python\envs\default`（隔离 venv），而 PATH 里的 `python` 是 `...\python\versions\3.13.12\python.exe`（基础解释器），**两者互相看不见对方的 site-packages**
- **降级**：一律用 venv 解释器执行
  ```bat
  C:\Users\yyx\.workbuddy\binaries\python\envs\default\Scripts\python.exe 02_import_to_mysql.py
  ```
  或先 `...\envs\default\Scripts\activate.bat` 再 `python xxx.py`。

### R14 · 把 `NA` 当歌手/曲名灌进库
- **信号**：页面 tooltip 出现"歌手：NA"；或 `SELECT COUNT(*) FROM spotify_songs WHERE track_artist='NA'` 返回 5
- **原因**：原始 `data.csv` 有 5 行把缺失写成了字面量 `NA`（不是空串），字符串判断 `== ''` 抓不到
- **降级**：清洗脚本已把 `NA / N/A / null / None` 统一转 NULL 并打 `meta_missing`。**别再手工 `sed` 改 CSV**，改脚本重跑。

## 14. 结论预设（写大屏文案/答辩时直接用，别再编）

这些都是从数据里算出来的，可以直接引用：

1. **供给量 ≠ 热度，且方向相反**：edm 供给第 1（6,043 首，18.41%）但平均热度垫底（34.83）；pop 供给第 3（5,507 首）却热度第 1（47.74），比 edm 高 **12.91** 分。
2. **子流派断层极深**：`post-teen pop` 56.83 vs `progressive electro house` 26.87，差 **29.96** 分。edm 的 4 个子流派里 `progressive electro house`(26.87)、`big room`(32.28)、`electro house`(35.51) 全部排在 24 个的末 6 位 —— edm 的"高供给低热度"是被自家电音子类拖下去的（唯一例外是 `pop edm` 45.69）。
3. **最大赢家是 edm，最大输家是 rock**：以 2010 年为界，edm 占比 2.03% → 24.43%（**+22.41 pct**）；rock 39.12% → 6.23%（**−32.89 pct**）；同期 pop +11.97 pct、latin +7.56 pct、r&b −9.35 pct、rap 基本持平（+0.31 pct）。
4. **近十年更细的趋势**（2010–2013 → 2017–2019）：rap **12.3% → 20.2%（+7.9）** 是真正的后期赢家；edm +4.0、latin +3.4；pop **−6.9**、rock **−6.7** 双双回落；r&b −1.7。
5. **音频特征能把流派干净地分开**：edm 是 energy 0.803 最高 + instrumentalness 0.219 最高 + valence 0.401 最低（"高能、器乐化、不快乐"）；rap 的 speechiness 0.198 是 pop 的 **2.7 倍**（说唱本体）；latin valence 0.606 最高（"快乐值"最高）；r&b acousticness 0.260 最高、energy 0.591 最低（最"软"）；rock danceability 0.521 最低（最不适合跳舞）。
6. **高分热度池被 pop/latin 垄断**：81-100 分箱仅 1,340 首（4.08%），其中 latin 27.1% + pop 26.6% 合占 **53.7%**；edm 在该箱只有 9.7%，而在 21-40 箱占 26.6%。
7. **必须写的口径提醒**：本数据集是"6 流派 × 4 子流派 × 每流派约 79 个歌单"的固定采样（共 471 个 `playlist_id` / 449 个 `playlist_name`，每流派 4,951–6,043 首），所以第 3/4 条的"崛起/衰退"只能表述为**"歌单供给结构的变化"**，不能写成"全球音乐产量"。这句话写进大屏副标题，答辩时能挡掉一半质疑。
