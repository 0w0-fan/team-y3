# 数据字典 · spotify_songs

> 库：`spotify_dashboard`　表：`spotify_songs`　行数：32,833　列数：23　字符集：utf8mb4 / **utf8mb4_bin**
>
> 数据原样入库，未做清洗。由 `shared/scripts/01_import_raw.py` 导入。
>
> ⚠️ **排序规则必须是 `utf8mb4_bin`（区分大小写）。** 若用默认的 `utf8mb4_general_ci`，
> `Billing` 和 `BILLING` 会被当成同一个名字，`COUNT(DISTINCT track_artist)` 从 **10,693 掉到 10,684**，
> `COUNT(DISTINCT track_album_name)` 从 **19,744 掉到 19,515**，歌手和专辑维度的分群结果直接错。

## 一、字段说明

### 标识与文本

| 字段 | 类型 | 说明 | 需要注意 |
|---|---|---|---|
| `id` | BIGINT | 自增主键 | 原始数据无主键，导入时生成 |
| `track_id` | VARCHAR(64) | 歌曲唯一标识 | 28,356 个唯一值，**32,833 行里有 4,477 行是同一首歌被多个歌单收录** |
| `track_name` | VARCHAR(512) | 歌曲名 | **5 行是字面量字符串 `NA`**（原表 R write.csv 的缺失值写法），不是 NULL |
| `track_artist` | VARCHAR(512) | 歌手 | 同上 5 行为 `NA`；**未拆分合作艺人**，`&` 多为乐队名分隔符 |
| `track_album_id` | VARCHAR(64) | 专辑唯一标识 | — |
| `track_album_name` | VARCHAR(512) | 专辑名 | 19,744 张专辑，**中位数只有 1 首** |

### 歌单分类（这是不去重的理由）

| 字段 | 类型 | 说明 |
|---|---|---|
| `playlist_name` | VARCHAR(255) | 歌单名，共 449 个 |
| `playlist_id` | VARCHAR(64) | 歌单唯一标识 |
| `playlist_genre` | VARCHAR(64) | 6 大流派：pop 5507 / latin 5155 / r&b 5431 / rap 5746 / rock 4951 / edm 6043 |
| `playlist_subgenre` | VARCHAR(128) | 24 个子流派 |

> 同一个 `track_id` 出现在不同歌单时，只有上面 4 个字段不同，音频特征与热度**完全一致**。
> 这 4 个字段本身就是分类维度，删重复行等于删掉「这首歌属于哪些歌单」的信息。
> 需要歌曲级去重时，在第二阶段自己建视图：`SELECT ... GROUP BY track_id`。

### 日期

| 字段 | 类型 | 说明 |
|---|---|---|
| `track_album_release_date` | VARCHAR(64) | **原始字符串，未加工**。三种格式混存 |

格式分布（实测）：

| 格式 | 行数 |
|---|---|
| `YYYY-MM-DD` | 30,947 |
| `YYYY`（只有年份） | 1,855 |
| `YYYY-MM`（只有年月） | 31 |

> ⚠️ 常见误区：`1,886 = 1,855 + 31`，这是「无法按 `YYYY-MM-DD` 解析」的总数，
> 不是「只有年份」的数量。只有年份的是 **1,855** 行。
>
> 做月度或趋势分析前，先按需转换。**但不要在公用表上转**，转 DATE 会丢掉「只有年份」这层信息，
> 而且把 1,855 行补成 1 月 1 日等于编造数据。

## 二、已知数据特征（做分析前必读）

| 特征 | 数值 | 影响 |
|---|---|---|
| 唯一 `track_id` | 28,356 | 直接 `COUNT(*)` 数的是「歌曲-歌单」记录，不是歌曲数 |
| 全行完全重复 | 0 | 没有需要删的重复行 |
| 2020 年记录 | 785 行（占 2.4%） | 数据抓取时点截断，**做年度趋势请截止到 2019** |
| 专辑曲目数中位数 | 1 | 专辑维度结论较薄，不宜作主分析 |
| 歌手作品数中位数 | 1 | 10,693 位歌手，作品数 ≥3 的仅 2,486 位 |
| 音频特征与热度相关性 | 最强仅 \|r\|=0.150 | **「某特征决定热度」这类结论在这份数据上不成立** |
| 字面量 `NA` | 5 行 × 3 列 | 统计时要当缺失处理，否则会多出一个叫 NA 的假歌手 |

## 三、第一阶段刻意没做的事

| 没做 | 原因 |
|---|---|
| 不删行、不去重 | 见上文「歌单分类」 |
| 不把 `track_popularity=0` 置空 | 0 是真实值 |
| 不转日期类型 | 1,886 行格式不标准，转换会丢精度或编造数据 |
| 不处理字面量 `NA` | 原样入库，留给各方向第二阶段按自己的口径决定 |
| 不建派生列 | `release_year`、`duration_sec`、热度分箱等由各方向自建 |
| 不拆歌手名 | `&` 是乐队名分隔符，拆了热度无法分摊 |

## 四、常用查询片段

```sql
-- 歌曲数（去重口径）
SELECT COUNT(DISTINCT track_id) FROM spotify_songs;  -- 28356

-- 歌手作品数 TOP10（第二阶段自己建视图时可参考）
SELECT track_artist, COUNT(DISTINCT track_id) n, ROUND(AVG(track_popularity),2) avg_pop
FROM spotify_songs
WHERE track_artist IS NOT NULL AND track_artist <> 'NA'
GROUP BY track_artist ORDER BY n DESC LIMIT 10;

-- 发行年份分布（从字符串截取，不转 DATE）
SELECT LEFT(track_album_release_date,4) y, COUNT(DISTINCT track_id) n
FROM spotify_songs
WHERE track_album_release_date REGEXP '^[0-9]{4}'
GROUP BY y ORDER BY y DESC LIMIT 12;
```
